# Bot 单场回放审查

回答：**Bot 在什么局面下，为什么选择这些行动，实际做成了什么，是否兑现设计承诺？** 先建立行动层证据，再解释统计指标。机制调用次数、低 Drop、高胜率都不能单独证明策略质量；缺陷也不会使全部原始统计自动失效，应指出具体受影响的解释。

在 Ingress Arena 仓库使用时，先读 [references/ingress-arena.md](references/ingress-arena.md)，其中提供归档定位、回放验证和决策还原入口。其他项目沿用下面的方法，按自身规则与回放格式取证。

## 确定检查对象

- 优先检查用户指定比赛。未指定时，通常先选 1～2 场已有 Development 回放，记录选样理由；选中位样本、固定地图或异常样本均可，但标明是否定向挑选。不要为找到支持原假设的例子持续换样本，也不要为抽查消耗未开放的 Holdout。
- 冻结比赛身份：运行目录、比赛 ID、地图、双方策略 ID／版本／完整参数、规则配置、seed、换边腿和阵营映射、构建来源。用该批次实际设计文档建立预期；策略名称和代码注释只是线索，不能代替行为证据。
- 汇总表可以帮助选样。选定后进入具体比赛，不把请求扩展为统计重分析、策略寻优或大批重跑。审查默认产出证据与建议，正式修复按用户当前授权范围处理。

## 建立可信回放

区分两种验证：**规则回放验证**证明记录的提交可产生记录的结果；**策略决策复现**证明所用策略实现可产生记录的提交。前者不自动证明后者。

1. 用项目回放器验证输入、逐轮状态和最终结果，并核对所选逐场记录。不要只验证最后比分相同。
2. 还原决策时加载归档配置和策略参数，保持初始化调用、随机流、出生选择、历史记忆及命令顺序。不要用当前默认参数替代归档值，也不要每轮新建一个丢失记忆的 Bot。
3. 若原始回放缺失，优先从完整归档输入重执行单场，输出到新目录，并核验原记录。无法匹配时明确复现缺口；仍可报告档案中可直接观察的事实，但不能把新轨迹或未匹配的内部 trace 当作原策略行为。
4. 开发视角可以用于解释结果，替代行动和策略价值计算仍只使用 Bot 当时合法获得的信息。不要要求 Bot 响应当时不可知的敌方位置或私有资源。

保留原回放和历史产物。临时观测代码优先复用原实现，在独立临时目录或 checkout 中工作；增加观测后，核对未改变的策略逐轮提交与原档一致。验证失败时先解释差异，不继续作精确决策归因。

## 从全场扫描进入关键行动

先浏览整场的开局、首个得分结构、争夺／失守、资源交接、增援、终局，形成简短时间线。既看行动，也看**谁在什么时候没有行动**，避免只筛选成功事件而漏掉休眠、振荡或长期赶路。

选取能回答问题的关键窗口，从触发前跟到任务完成、失败或放弃。对窗口记录以下链条；无法观察的环节标为未知，不从结果倒推：

| 环节 | 要记录的证据 |
|---|---|
| 当时局面 | 轮次、Agent／目标身份、合法可见状态、位置／距离、资源、现存收益和威胁 |
| 规划与评价 | 活动计划、候选任务、关键评分／门槛、未选候选；必要时追踪评分函数是否真正接入调用路径 |
| 分配 | 谁获分什么任务、容量／预留、角色切换、哪些人员无任务及原因 |
| 提交与执行 | 有序命令、成功／Drop／无操作、同轮竞态、对象生命周期变化 |
| 实际收益 | 恢复多少 HP、提前几轮得分、保住或摧毁什么、净耗费资源和行动机会 |

优先读取原有决策日志。必要时临时记录候选与分配，或通过原有模块作影子决策并逐轮对齐提交。只有公开事件时，能说明发生了什么，未必能说明为何选它。终端展示关键窗口和结论，完整 trace 写入文件，避免打印整个状态对象淹没证据。

## 按行为机制检查，避免只看计数

按比赛实际机制选用以下问题，不要求每场都出现所有机制，也不预设所有 Bot 都有问题。

| 检查面 | 微观核对重点 |
|---|---|
| 建造与规划 | 计划是否可达、可完成；失效后是否重规划；路线／资源前置是否重复；一个局部计划是否长期占住全部任务供给 |
| 防御 | 伤害或威胁属于当前目标生命周期吗；实际恢复量是否为零；到达时间是否晚于预计失守时间；补血能否延长有效得分，而非仅增加调用次数 |
| 攻击 | 是否打到预期目标；必要攻击量、可同时到达的人员与任务容量是否匹配；消除收益和夺点收益是否发生；攻击机会成本是否因其他策略闲置而被夸大或低估 |
| 运输 | 交接是否比持有者直接行动更早完成任务；谁等待、谁多走路；资源是否随后被使用；接收者是否因提交时序被迫再等一轮 |
| 阻断 | 阻断评分是否实际改变选择；只是普通建造顺带相交，还是改变了对手可行机会；是否计入自身空间损失，是否存在多个可替代候选 |
| 分工与空闲 | 无候选、分配失败、等待资源、赶路、执行失败、主动保留分别有多少；增援是否进入有效任务流；是否重复预留、往返切换、无收益 Move |

分母按实际可决策的 Agent-round 计算，增援出现前不计入；“无任务”“无提交”“没有成功动作”分别记录。等待可能是必要协作，移动可能在履行任务，不能一律标成浪费。反过来，低 Drop 可能只是提交很少，不能掩盖无人干活。

## 用局部对照检验解释

怀疑行为低效时，找一个具体、合法、可比较的替代行动：如持钥者直接连线、取消满血补血、同一观察下关闭一个 overlay。核对规则限制、资源、距离、同轮顺序和机会成本，再给出判断。

- 区分“规则允许”“当轮可获益”“局部窗口更优”和“整场策略更强”。某轮可提前连线不等于最终必胜；去掉交接会改变之后的资源、路线和决策。
- 无 overlay 对照保持同一观察、核心状态、配置和随机流；换一个 Bot 或出生点不构成干净消融。比较实际命令／分配的变化，而非只看到正评分就宣称机制产生效果。
- 需要窗口反事实时，从一致的状态和策略记忆开始，使用相同规则和随机流，独立推进反事实后续。若只能固定敌方原命令，明确它没有模拟敌方适应；不要只改一个动作却沿用全部原后续结果计算胜负。
- 实现定位要沿行为追到生产调用路径：区分候选生成、评分、分配、执行、观测／记忆缺陷与规则约束。定义了价值函数或通过函数测试，不证明策略使用了它。

一个可复现反例足以推翻“永不满血补血”之类的绝对承诺；一两场不足以估计普遍发生率，也不足以证明某参数无效或规则必然失衡。

## 交付与停止条件

默认交付简短审查结论和可复核的证据文件；发现少则少报，无异常则说明实际检查过的行为。每个发现包含：

- **证据**：比赛／轮次／Agent／目标、当时条件、实际动作和效果，以及回放或 trace 指针。
- **判断**：是否符合设计、已证实缺陷或待验证假设、调用路径定位；无需强行给每个异常找到唯一根因。
- **影响与下一步**：它会误导哪个指标或机制结论，最小修复／验证场景是什么。只报告本次真正执行的对照和验证。

当所选比赛已验证或明确受限、关键行为链和不确定性已解释、主要发现可复核时，完成抽查；不要为了得到置信区间自动扩大批次。若行为缺陷会混淆参数效应，建议先修复并版本化策略、重放局部回归，再评估是否需要重跑受影响的统计。保留原始数值，收紧不受支持的因果解释。
